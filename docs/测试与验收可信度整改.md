## 可复现流程

在根目录执行：

```powershell
.\verify-course.ps1
```

前提是 MySQL 已启动，MySQL 客户端、JDK、Node/npm、Python 可用，前端依赖及 `AI_Server/venv` 已按 README 安装。

脚本从 `.env` 读取数据库凭据（不输出），也可设置 `TEST_DB_USERNAME/TEST_DB_PASSWORD`。每次生成随机 `lifetrack_test_*`，在其中执行冻结总脚本并登记基线，然后运行全部测试。默认成功和失败都会清理该次测试库；`-KeepDatabase` 可留库排查，记录会明确显示未清理。

测试必须使用独立库，且需要创建/清理测试库权限。仅测试 classpath 注册的初始化器在连接前检查库名；即使某个测试使用 dev profile，也不能绕过。实际反向验证中，未设置 TEST_DB_URL 的 Spring 测试在连接前失败。这是预期的保护验证，不计作业务回归失败，也不能拿其旧失败报告混入后续通过结果。

脚本在运行前只移除上次 Surefire 报告，不清理编译类，避免影响正在运行的开发服务。任一命令非零、用例失败/错误/跳过、无用例、少跑一个必需阶段或执行期间源码变化，都不能生成通过结论。

机器结果位于 `docs/verification/<runId>/`：

- `summary.json`：运行环境、源码指纹、命令退出码和清理状态。
- `cases.json`：JUnit 逐项名称、耗时、结果与证据层级，不复制失败正文、Token 或请求数据。
- `sources.json`：本次执行代码的逐文件 SHA-256；文本换行统一为 LF，兼容不同检出平台。
- `checksums.json`：机器证据文件的校验值。

原始日志位于 Git 忽略的 `.verification/<runId>/`，其原始字节哈希记入摘要。日志不随代码推送。对公开证据与当前源码可执行：

```powershell
.\verify-course.ps1 -CheckEvidence docs/verification/<runId>
```

指纹用于发现文件变化，不是数字签名，也不能单独证明结果不可伪造；可信度来自可复现执行、独立测试库、分层断言和可核对的原始日志。报告中的基准提交加 workingTreeDirty 与源码指纹，准确描述提交前执行的工作树，不假装测试执行于一个尚未生成的提交。

## 测试能证明什么

| 层级 | 能证明 | 不能替代 |
| --- | --- | --- |
| 单元测试 | 状态、计算、校验和受控故障规则 | 真实数据库约束与完整 HTTP 流程 |
| 前端声明/页面逻辑测试 | 字段声明、状态计算、带桩交互逻辑和构建 | 真实后端兼容、浏览器点击 |
| 真实前端 HTTP 契约 | 原始前端请求封装可与真实后端/MySQL 完成闭环；仅 uni 平台传输桥用 fetch | DOM、样式、原生 uni-app/微信平台 |
| HTTP/MySQL 集成 | 认证、业务拒绝、事务、直接 SQL 结果、并发与持久化 | 页面布局与操作反馈 |
| 浏览器实际点击 | 本轮指定页面与操作在桌面及所测窄屏的实际表现 | 全设备兼容或可重复自动浏览器回归套件 |
| 真实模型脚本 | 特定时间、模型、输入下的实际输出 | 确定性核心业务回归，或模型输出永远稳定的保证 |

本轮不把已有真实模型脚本的历史结果算作重新通过；隔离脚本不调用真实模型。浏览器看板按产品本身逻辑可能自动请求报告，但本轮未据此对模型质量作验收结论。未录制课程演示视频，不将截图视作视频。

## 现场脚本与浏览器证据

`backend/scripts/verify-p1-acceptance.ps1` 和 `verify-business-rules.ps1` 可指定 `-Token` 使用专用账号；未指定时使用共享开发账号。共享账号下全局按自然日去重，新增三条打卡不一定让全局增加三天，脚本必须与真实日期集合比较。

## 为什么 Flyway 从 V2 开始

用户要求“本次全部数据库调整先放总脚本，调整之后再正式启用 Flyway”。因此交接顺序是：

1. `backend/sql/init_db.sql` 建立本次最终结构，包含此前全部表、字段与约束。
2. 首次接管检查结构并在 `flyway_schema_history` 登记 `version=1, type=BASELINE, success=1`。
3. 此后的第一项结构变化才写成 `V2__描述.sql`，随后 V3、V4。

**版本 1 在这里是数据库基线记录，不是漏写的 V1 文件。** 它表示“截至版本 1 的结构已在库中，Flyway 从之后开始管理”。本仓库没有 `V1__建表.sql`，避免让已由总脚本建好的表再次建一遍。

新项目如果从第一天就完全交给 Flyway，通常可以使用 V1 建表；本项目选择基线接管，是为了满足这次明确的交接要求。不能再补一个 V1 并期待它在当前版本 1 的基线上执行。本轮未增加业务 DDL，无须创建 V2。未来若要改表，再新增真正的 V2 迁移。
