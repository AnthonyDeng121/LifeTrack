# AI预览前置周期校验修复

用户现场截图：开始2026-12-30，结束2026-11-28，目标20天，却进入AI拆解。

原因：createTask在AI尚无有效预览时，提前return generatePreview；周期校验位于该分支后，仅在保存阶段执行。generatePreview只检查标题，后端TaskPreviewRequest也没有日期字段。手动保存有校验不能证明AI预览已校验，这个遗漏属实。

修改后：

1. 前端抽取validateCreatorForm，首次生成、按钮重新生成、确认保存统一先校验。非法输入只提示，不切换creating状态，不发AI请求。生成期间禁止修改周期和目标。
2. AI预览请求携带startDate、endDate、targetDays。后端DTO要求三项必填，TaskService在请求模型前复用validateTitle/validatePlanPeriod，拒绝缺失、倒置周期、目标越界和不支持年份，返回400。
3. 更新所有现行真实模型探针和契约调用，不能继续依赖省略周期的旧预览协议。预览仍不写入计划。
4. 前端实际组件逻辑验证截图日期下首次/重新生成/已有预览保存均0次AI调用；目标超出周期也0次。后端单元验证AIService未被调用；真实HTTP/MySQL验证400及无计划写入，前端实际HTTP封装同样覆盖。

这是前置条件与副作用顺序的回归：昂贵外部调用和写入前先检查共同条件，不能把保存校验放在某个模式分支之后。质量检查和日期检查是两件事，不能依赖模型拒绝非法表单。

本轮不改学习进度、打卡、时长或数据库结构；截图继续只保留本地。最终证据见最新verification索引，未把带桩组件测试写成真实浏览器操作。
