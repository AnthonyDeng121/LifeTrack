## 本次任务目标及修改前后区别

本次修复用户提出的三个问题：现有计划无法新增学习步骤、编辑弹窗关闭按钮偏离右侧、AI 故障期间的手动打卡无法补回学习进度。

修改后，计划详情提供“新增子计划”，新增和编辑复用弹窗；用户可以自行增减步骤，但至少保留一个。弹窗关闭按钮取消默认按钮外边距和内边距，使用固定尺寸与 Flex 居中，在桌面和窄屏下均靠标题行右侧。

记录页仍为唯一学习记录输入页面。AI 故障时，选择计划后点击“保存记录并打卡（待补分析）”，原始内容、明确时长和上海业务日期会持久化。AI 恢复后，在同页的“待补分析”列表点击“补分析”，按原日期补回实际学习进度，不重复生成打卡。

## 领域模型与实现方法

新增 `DeferredLearningRecord`，记录用户、计划、内容、时长、原始时间、分析状态和最近一次分析说明。其状态为：

- PENDING：已经持久化，等待 AI 分析；故障重试后仍不可用则保持此状态。
- APPLIED：分析已产生实际进度并在同一事务中写入；拒绝重复应用。
- UNMATCHED：分析完成但没有有效匹配；保留原始内容和手动打卡，允许以后重试，不虚构进度。

补分析先锁定记录，再锁定所属计划；状态变更、步骤进度、行为日志和统计更新使用同一事务，任何写入失败共同回滚。历史时间由数据库保存的记录提供，外部 API 不能随意指定历史日期。已过期计划允许处理当时周期内的已保存记录；已取消计划及原日期已经不在修改后的周期内的记录不会被强行应用。

普通记录和历史补分析复用 ActionService 的匹配、候选归属校验、实际贡献裁剪和加权进度计算。补分析的行为日志沿用原始时间及原始分钟数，避免将昨天的学习计到今天。每日时长由已应用行为日志和仍未应用的故障记录汇总，补分析不会再累计一次原时长。

旧版手动打卡可点击“导入旧版手动打卡”生成待分析记录。导入按原打卡日期保存，不按导入当天保存；已存在待分析记录或当天已有有效进度日志时跳过，以防旧数据缺少关联信息导致重复计算。导入不会直接修改学习进度。删除计划时会同时删除其故障记录。

子计划新增接口先校验归属、内容、权重和数量，再按旧权重比例分配剩余份额；所有旧权重为零时改为平均分配。最后一项吸收四位小数的舍入余量，保证权重合计为 1。删除同样使用此算法，禁止删除最后一个步骤。新增不清空旧步骤的学习进度，新步骤从零开始；主计划进度按新权重重新计算，因此增加未完成步骤后总进度可能下降，这是学习范围增加后的真实变化。

数据库权重调整为四位小数，计划总进度调整为四位小数，避免数据库舍入破坏权重合计。前端统一按接口的百分数显示，修复 1% 被误当成比例值再次乘以 100 的问题。

## API 与数据结构变化

- `POST /api/v1/tasks/{taskId}/subtasks`：新增子计划。
- `POST /api/v1/actions/deferred`：保存故障记录，同一天允许多条记录，正式打卡仍最多一条。
- `GET /api/v1/actions/deferred`：查询当前用户的故障记录。
- `POST /api/v1/actions/deferred/{id}/retry`：补分析；重复处理返回 409。
- `POST /api/v1/actions/deferred/import-legacy`：导入可识别的旧版手动打卡，重复导入不会新增记录。

开发环境沿用 JPA `ddl-auto:update` 建表及调整字段精度。新增表为 `deferred_learning_records`，不引入队列、定时任务或额外服务。补分析由用户主动触发，AI 恢复后不会在后台悄悄修改用户进度。

## 可学习与课程报告内容

1. 将“人工确认出勤”和“AI 识别学习进度”分开，避免外部服务故障破坏核心业务闭环。
2. 用持久化状态机描述故障恢复，而不是仅弹出错误提示后丢弃内容。
3. 使用行锁与事务保证重试只应用一次，数据库唯一约束保证出勤不重复。
4. 区分事件原始时间与处理时间，保证历史重放不污染今天的统计。
5. 动态增减步骤涉及权重归一化、数据库精度和总进度重算，需要同时验证前端展示和数据库数据。

代表性用户 Prompt：用户需要自行增减子计划，关闭按钮错位，AI 故障期间手动打卡后进度应如何恢复。AI 辅助分析后，采纳了“持久化待分析记录＋显式补分析”的方案；实际开发补充了历史导入、并发防重和时长去重，并通过业务测试和真实浏览器验证。
