# 技术复盘与答辩要点

提交人：邓宇轩　学号：2411006。整理日期：2026-10-28。

本文总结当前实现中可核对的技术取舍，不代写未经本人确认的个人感想或经历。

## 为什么不能只禁用按钮

两个窗口、断网重发和直接请求都会绕过前端按钮状态。正式打卡由计划行锁与数据库`(user_id,task_id,check_in_date)`唯一约束共同保护；学习记录通过`requestId`及数据库`(user_id,request_id)`唯一约束识别同一次提交。相同请求重发不再生成第二条原文，相同标识搭配不同内容返回冲突。

## 为什么原文先保存，分析成功再计时

模型请求会失败或超时。先用短事务保存原文，再无写锁请求模型；成功时将实际进度、用户填写时长、自动打卡和应用状态原子提交。失败保留原文但不计时。重新分析在锁内再次校验状态，避免两个请求同时累计。模型返回的时长不可信，不能覆盖用户明确输入的分钟数。

## 三种完成概念如何解释

人工结束表示停止执行，不等于达到学习成果。学习成果完成要求所有步骤完成，但这是用户记录与确认，不等于客观测量知识掌握程度。打卡目标表示坚持天数，按真实日期计算。按照最终需求，即使学习完成率100%，有效期内仍可打卡，继续记录真实坚持天数，不重新打开或篡改学习进度。

## 数据分页与统计为什么要分开

历史每次默认读取20条，依靠数据库分页和稳定的日期、时间、ID排序；待分析状态在数据库过滤。修改筛选条件回到第一页，最后一页处理空后回到有效页。连续天数和完成率按完整日期集合计算，不能只数当前页；看板不再读取所有历史正文，只读日期和最近七天详情。

## AI建议需要怎样复核

一次常规回归通过后，组合操作仍暴露出旧备注覆盖、权重变零、旧表单覆盖及撤销后时长未归零等缺陷。复核应先写可复现反例，再修规则并重跑；不能用更多测试数量证明未覆盖场景正确，也不能把带桩或受控AI测试称作真实模型质量测试。

## 可现场演示的检查点

1. 计划完成后在有效期内打卡，刷新历史可见；同日重发返回409。
2. 输入1小时30分钟，成功累计90分钟；失败记录保留为未计入，重试不重复累计。
3. 两个窗口编辑，旧版本提交返回409，先前修改保留。
4. 新增或修改权重，不允许任何步骤缩到1%以下。
5. 分页翻至最后一页，处理最后一条待分析记录后自动退回有效页。
6. 取消一个计划后历史仍可查询，但退出看板与AI反馈的数据范围。
