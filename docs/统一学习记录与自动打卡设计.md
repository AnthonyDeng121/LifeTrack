# 统一学习记录与自动打卡设计

## 需求与前后区别

原有系统存在两个输入入口：记录页通过 AI 推进学习步骤，计划详情的每日打卡表单仅保存出勤。用户容易把打卡成功理解为学习进度增加。

本次保留独立记录页作为唯一学习内容输入页面。默认由 AI 匹配计划和步骤；用户也可在同一页面选择一个进行中的计划，再由 AI 匹配步骤。详情页保留学习进度、打卡概览、历史和步骤管理，提供前往记录页的导航。

## 业务规则

1. 正式打卡仍按用户、学习计划、上海业务日期计算，每日最多一条，数据库唯一约束继续保留。
2. 首次实际增加步骤进度的记录，自动生成该计划的当天打卡。同一天后续有效记录继续更新学习进度，不新增打卡。
3. 一条输入可以匹配多个计划或步骤。各计划独立计算是否首次打卡，同一计划的多个步骤只触发一次打卡。
4. 无匹配、无正向贡献、AI 不可用时不保存成功记录、不自动打卡。前端保留输入供修改重试，不显示保存成功。
5. 仅当前用户、进行中、处于有效日期区间的计划可以接受记录。AI 返回的步骤 ID 必须位于服务端候选集合内。
6. 单步骤单次增量不超过 0.30，步骤累计不超过 1.00。日志保存实际增量，撤销时按实际值回退。
7. 自动生成的打卡有 automatic 标志。撤销当天最后一条有效记录时删除对应自动打卡；已有旧版手动打卡不受影响。还有有效记录则保留打卡并更新时长与内容。
8. 学习进度按步骤权重加权；打卡完成率按实际打卡天数与目标天数计算。两者分别展示。
9. AI 服务故障通过 analysisUnavailable 显式反馈；同一记录页提供选择计划后的手动打卡降级，不自动增加步骤进度，后端继续验证周期、归属和每日唯一性。

## 实现方法

复用 ActionLog、SubTask、Task 和 CheckInRecord，不引入额外服务。ActionService 的事务中完成有效记录保存、步骤进度更新、计划进度重算和打卡维护，失败共同回滚。

记录流程使用 READ_COMMITTED 隔离级别，按计划 ID 顺序获取悲观写锁，减少并发覆盖进度或重复创建打卡的风险；旧手动打卡接口共用计划锁，数据库唯一约束最后兜底。当前课程项目会在 AI 分析期间持有计划锁，适合本地低并发演示；如果日后扩展并发量，应将 AI 分析移出写事务，写入时重新校验候选、状态和进度。

AI 输入中同时提供计划标题和步骤内容。后端不直接信任 AI 的步骤 ID、增量或重复匹配。多步骤匹配时分摊输入时长，避免看板重复累计；自动打卡的日时长根据有效日志重新汇总。

前端补全遗漏的 durationInput 参数，并支持可选 taskId。响应新增 taskId、subTaskId、subTaskTitle、checkedInNow，用于明确展示匹配对象、步骤实际增量、计划总进度和打卡结果。

数据库通过现有开发环境 ddl-auto:update 添加 check_in_records.automatic 可空列，旧记录保持兼容。正式迁移可执行：`ALTER TABLE check_in_records ADD COLUMN automatic BIT NULL;`（列不存在时执行）。

## AI 辅助开发记录与报告要点

- 用户 Prompt：统一记录入口，首次有效记录记为打卡，后续重复记录只推进进度，保留课程防重复打卡要求。
- 采纳的设计：区分学习事件与每日出勤，保留独立记录页面，详情页仅展示和管理。
- 实际修正：发现前端丢失时长参数；修复无匹配也提示保存成功；将 AI 贡献校验、进度封顶和打卡防重放在服务端。
- 可用于报告的知识点：领域概念拆分、事务一致性、业务幂等与数据库唯一约束、AI 输出的后端校验、前后端 API 契约测试、撤销操作的数据闭环。
- 验证方式：后端 ActionServiceTest、原有计划和打卡回归测试；前端契约、记录页实际提交逻辑和 H5 构建；三端运行时验证真实 AI、持久化进度和打卡统计。
- 本次自动化验证结果：加载本地数据库环境配置后执行 Maven clean test，39 项测试通过；npm run verify 的 API 契约、核心提交流程（含 AI 故障手动打卡降级）及 H5 构建通过。

## 联调操作

创建合法周期内的学习计划及步骤，在记录页选择该计划：先输入无关内容，确认不打卡；再提交相关学习内容，确认进度增加且首次打卡；再次提交不同学习内容，确认继续增加进度但打卡天数不变。进入计划详情查看统计和历史；依次撤销有效记录，确认最后一条撤销后自动打卡消失。独立重复调用旧版手动打卡接口仍应被拒绝。
