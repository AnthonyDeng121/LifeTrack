# 2026-10-29 第九至十三项复核

## 业务口径建议（第九项，未在本轮改变规则）

人工结束计划（ENDED）保留实际学习进度和打卡率，不能强制两项变成100%。人工确认一个步骤完成则该步骤为100%，计划学习进度按各步骤权重重算；所有步骤完成时学习进度才为100%。打卡率始终为真实打卡天数除以目标天数，学习和打卡双达标才COMPLETED。撤销早于人工确认的AI记录，不应抹掉后来的人工确认；这一撤销冲突仍待后续单独修复，不能把本轮加权统计修复当作它已解决。

## 时长查询澄清（第十一项）

计划总时长本来就在ActionLogRepository.sumLearningMinutes通过SQL SUM汇总全部成功日志。汇总当然要覆盖全部相关数据；数据库可能扫描相关索引或行，不能宣称完全不扫描。先前指出的具体问题是refreshAutomaticAttendance为了更新某一天打卡的时长，读取计划全部历史再在Java筛当天。可将该查询收窄为账号、计划、上海当天半开时间区间，在数据库聚合；本轮只澄清，没有更改这段逻辑，也不引入可能失配的累计缓存。

## 计划增量修复（第十二项）

步骤增量与计划增量必须分开：步骤权重25%，本次推进20%，贡献计划5个百分点。ActionLog保留contribution供步骤回退使用，新增plan_contribution记录发生时权重乘实际步骤增量。今日与七日进度趋势改为汇总该快照，后续编辑权重或解除步骤关联不会重写历史。跨计划数值是累计百分点，可以超过100，并非计划完成率。

新增Flyway V5，不修改V1—V4。历史有步骤关联的记录按迁移时权重估算；旧系统未存当时权重，不能承诺精确还原。关联已丢失的记录保留NULL、不计入增量，原时长和记录保留。新数据则在实际应用学习增量的同一事务中保存准确快照。

回归覆盖25%乘20%=5%、步骤权重变化后快照不变、取消计划排除、真实HTTP/MySQL读取持久化快照。统计仍完全不依赖AI。
