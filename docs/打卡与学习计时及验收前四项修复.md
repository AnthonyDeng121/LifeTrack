# 打卡与学习计时及验收前四项修复

日期：2026-10-27。

## 任务目标与范围

修复严格验收的前四项：学习记录覆盖手动打卡、权重分配退化为0%、旧编辑表单覆盖新修改、新增超长标题提示错误。第一项按用户新规则实现：手动只打卡，学习记录明确填写小时分钟，只有分析成功才累计学习时长，失败记录保留可重试。本轮不扩展计划内逐条学习历史详情，也不修改人工完成的业务政策。

## 修改前后

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 手动打卡 | 可填写备注，后续待分析记录可能改写它 | 无备注和时长输入，只记录出勤；旧备注不删除、不覆盖 |
| 学习时长 | 自然语言输入并依赖模型返回时长 | 小时、分钟数字输入，合成1～1440整数分钟，模型无权改写 |
| 分析失败 | 需要另点保存待分析，还可能直接打卡并累计时长 | 原文先保存，失败不计时、不自动打卡，按记录ID重新分析 |
| 重新分析 | 待分析和日志时长容易混在同一汇总路径 | 只汇总成功日志；状态与进度同事务应用，并发重试只能成功一次 |
| 计划累计时长 | 缺少明确的计划累计时长展示 | 详情显示成功日志合计的小时分钟 |
| 步骤权重 | 新增100%使原步骤变为0% | 全部分配结果先验证，每项至少1%，通过后才修改实体 |
| 编辑冲突 | 两次旧表单保存都200，先改的内容丢失 | 详情返回version，更新必须携带；过期409，缺失400 |
| 超长标题 | 落到数据库后被误报为409冲突 | 新增及编辑均在数据库前限制100字符，返回明确400 |

## 实现方法与报告要点

复用已有deferred_learning_records保存原文和填写时长，不新增表。原始记录先独立事务提交，AI请求不持有写事务和计划锁，避免慢模型阻塞手动打卡。分析成功时按父计划、原始记录顺序加锁，重查APPLIED状态，将日志、进度、自动打卡和处理状态原子提交。失败不进入action_logs，计划累计时长直接聚合成功日志，避免额外维护一个容易漂移的累计字段。

客户端版本协商与数据库锁解决不同问题：锁控制同一时刻的写入，version检查识别隔了很久才提交的旧表单。保存后flush取得新版本，前端冲突时保留草稿，允许载入最新内容重新编辑。

权重采用BigDecimal计算，先得到完整分配结果并校验下限，再修改实体，避免循环中途失败留下部分修改。DTO及服务共同校验标题；JSON反序列化拒绝把小数分钟截断为整数。上述都可作为“输入校验、事务边界、幂等与并发控制”的课程报告案例。
