## 开发环境如何启用

`dev` 是后端实例的配置环境，作用于连接该实例的全部用户，不是某种账号权限。

根目录 `.env` 设置 `SPRING_PROFILES_ACTIVE=dev`，执行 `./start-local.ps1 -WithAI`；本地脚本未读到环境配置时也会显式选用 `dev`。修改后重启服务。

手动启动时先设置数据库、JWT 等环境变量，再执行：

```powershell
$env:SPRING_PROFILES_ACTIVE = "dev"
cd backend
.\mvnw.cmd spring-boot:run
```

IDE 的 Active profiles 只填写 `dev`。`dev,prod` 等混合配置不算单独启用。开发环境默认开放一键登录与演示手机号登录；两项开关可单独关闭。不同手机号对应不同用户，一键登录复用公共开发账号。

数据库删除步骤时将关联日志的步骤 ID 置空，保留原始学习历史；删除整个计划时依次清理日志、步骤、打卡、待分析记录及计划，符合外键顺序。

旧库存在 5 条不属于任何计划的早期日志，贡献值为旧口径。保留原始数据；对已关联计划的日志强制贡献值在 0—1，未关联旧日志继续不进入计划统计。没有将历史值擅自转换或删除。

## 初始化与 Flyway 的交接边界

1. 使用 MySQL 8.0.16+。总脚本是 `backend/sql/init_db.sql`，包含本次所有结构改动。
2. 新机器直接执行总脚本即可建库建表。旧库先备份再执行；数据不满足约束时立即停止，不能以清空数据方式绕过。
3. 完成总脚本后，仅第一次启动设置 `FLYWAY_ADOPT_BASELINE=true`。接管策略检查关键约束和版本字段后登记版本 1。未显式允许接管的非空旧库会被 Flyway 拒绝。
4. 启动成功后移除该环境变量。后续启动正常执行 Flyway migrate/validate。`baseline-on-migrate=false`、`clean-disabled=true`。
5. 后续结构变化新增 `src/main/resources/db/migration/V2__描述.sql`，再依次 V3、V4。已执行版本不能修改；总脚本冻结，不再向已接管数据库重放。

注意：Hibernate 的 validate 不能代替所有索引和外键检查；本次通过执行真实总脚本、接管前关键结构检查以及数据库约束集成测试共同验证。

## 全量查询和 N+1 的解释

全量查询是先把全部候选数据读到 Java，再在内存筛选。例如用户有一万条计划，只想看进行中的十条，却先读取一万条。应该让数据库 WHERE 提前缩小范围。

N+1 是先查一次列表，再对列表中的每条记录各查一次关联数据。100 个计划逐个查步骤数量会执行 101 条 SQL。本次改为一条筛选计划 SQL 加一条按计划 ID 分组计数 SQL，共两条。列表仍保持现有接口形状；没有额外改变前端计划列表分页协议。学习历史继续固定分页。

全量数据并非永远不能读取：需要历史全貌的统计应读取相关范围；问题在于无关记录读入内存以及按行重复发起查询。

## 可用于课程报告的内容

- 展示“服务层业务验证 + 数据库 CHECK/外键/唯一约束”的两层防线，可用直接 SQL 证明绕过前端仍不能写入非法数据。
- 对比悲观锁与乐观锁：父行锁协调相关业务操作，version 保护过时实体；均不能代替业务状态检查。
- 绘制 AI 两阶段处理流程：快照读取 → 无锁 AI 分析 → 短事务加锁 → 快照校验 → 原子保存日志/进度/打卡。并发变化返回可重试的 409，而不是使用旧 AI 结果覆盖。
- 使用 Hibernate Statistics 实测查询次数，证明解决 N+1，而非只凭代码猜测。
- 展示 Flyway schema history 的 BASELINE 1 与测试库 V2 执行记录，解释历史脚本 checksum 为什么不能随意修改。
- 说明统一业务时区与服务器时区无关，跨部署机器仍保持相同的业务日期。

实现参考：[Spring Boot 数据库初始化与 Flyway 官方文档](https://docs.spring.io/spring-boot/4.0/how-to/data-initialization.html)。使用 Spring Boot 4 对应的 Flyway starter 与 MySQL 模块，避免仅添加 core 却未启用相应自动配置。
